# Windows 7 SP1 x64

The compatibility build targets Windows 7 SP1 x64 (6.1.7601). Build it on a
modern Windows machine; a new compiler's default output is not a guarantee
that its runtime supports Windows 7.

## Usermode tool

From the repository root, with CMake, Ninja and x64 mingw-w64 on PATH:

```powershell
cmake -S tool -B build/win7 -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_CXX_COMPILER=g++.exe -DNVTUNE_WINDOWS7=ON
cmake --build build/win7
ctest --test-dir build/win7 --output-on-failure
```

The option sets `WINVER` and `_WIN32_WINNT` to `0x0601`, the PE subsystem to
6.1, and defaults to static compiler runtimes. The tested w64devkit GCC 16.1.0
build imports only `ADVAPI32.dll`, `KERNEL32.dll`, `msvcrt.dll` and
`SETUPAPI.dll`, which are supplied by Windows. It does not need a GCC runtime
DLL or Visual C++ redistributable. Different toolchains can have different
imports and must be checked on the target OS.

The CMake option also accepts MSVC through the VS 2019 v142 toolset, with a
static runtime by default. That alternative has not been runtime-tested in
this validation. Current v143/v145 usermode runtimes are intentionally
rejected by this compatibility configuration. A normal build without
`NVTUNE_WINDOWS7` keeps its normal compiler/runtime configuration.

Copy `build/win7/nvtune.exe` to the target. `--help` and `fields` work without
a loaded driver or NVIDIA GPU. Register access requires an elevated process,
the driver below, and a supported physical NVIDIA card.

## Kernel driver and development installation

The driver remains plain WDM, with the same IOCTL ABI, administrator ACL,
NVIDIA device checks and register allowlist. The manual build targets kernel
6.1 and uses `/GS`, `GsDriverEntry` and `BufferOverflowK.lib` for the Windows 7
security-cookie startup. Kernel imports are `ntoskrnl.exe` and `HAL.dll`.

Run `driver/build.cmd` from an x64 MSVC/WDK environment as described in
[driver/README.md](driver/README.md). The validated manual build used MSVC
14.51.36231 and WDK 10.0.28000.0, with `/W4 /WX`. Kernel code does not link
the usermode C++ runtime. The `.vcxproj` now targets `Windows7`; its MSBuild
path needs a WDK that still supplies legacy target metadata. Current WDK
28000 rejects that integrated target before compilation, so use the verified
manual build path with that kit.

Windows 7 x64 requires an acceptable driver signature. For a development
VM, create the signed package on the build host with
`driver/sign-for-target.ps1`; that script uses newer certificate-generation
cmdlets which are not present on stock Windows 7. Copy only the signed SYS,
public CER and installer to the target, keeping the private signing key on
the build host. Install current Windows 7 SHA-2 support and servicing updates
(the test target had KB4474419 and KB4490628).

On a dedicated test target, from elevated PowerShell:

```powershell
.\install-driver.ps1 -EnableTestSigning
# Reboot the target before installing the test-signed driver.
.\install-driver.ps1 -Install -SysPath .\nvtunedrv.sys -CertPath .\nvtunedrv-cert.cer
.\install-driver.ps1 -Status
```

The target-side installer and the installer generated by `sign-for-target.ps1`
work under stock PowerShell 2.0. `-CertPath` imports the public certificate
into the target's LocalMachine Root and TrustedPublisher stores. The service
is demand-start. Test signing and certificate trust are target machine
settings; Druta does not change them. A test-signed binary is a development
artifact, not a production-signed driver release.

After each subsequent target reboot, start the service again from elevated
PowerShell with `.\install-driver.ps1 -Start` (or `sc.exe start nvtunedrv`)
before using timing functions.

To remove the development service, run `-Uninstall`. Remove only the test
certificate you installed, identified by its thumbprint, from both stores.
Restore the target's previous test-signing setting and reboot.

## Validation scope

Validation used Windows 7 Ultimate SP1 x64 in VMware Player 17. The signed
driver installed under PowerShell 2.0 and reached `KERNEL_DRIVER RUNNING`
with zero service/Win32 errors. Read-only IOCTL checks returned ABI 1,
driver version `0x10000` and eight mapping slots. Invalid sizes, handles,
read counts, unknown requests and a non-NVIDIA virtual PCI device were
rejected. An administrator could open the device; a restricted token with
the Administrators SID marked deny-only was denied access.

The static GCC executable ran on that same Windows 7 guest: `--help` and
`fields` exited 0; `list` and `set --dry-run` returned a clear no-NVIDIA
error with exit 1. Conflicting modes and `restore --dry-run` returned usage
status 2. Druta parsed all 33 fields from the real executable and reported a
failed preview on the non-NVIDIA adapter without retrying a write command.

The CLI regression suite uses real command parsing and planning with fake
PCI, BAR0 and platform implementations. It verifies that explicit previews,
including forced and unchanged previews, do not request writable mappings,
write registers or create backups; commits write only to that fake backend.
Conflicting flags and previews on unsupported commands fail before device
access. See [tool/README.md](tool/README.md) for the wrapper contract.
All 17 cases passed in Release builds with GCC 16.1.0 and MSVC 19.51 on the
Windows 10 host, and the static GCC test executable passed on Windows 7.

The VM has no physical NVIDIA GPU. Driver loading and command execution on
Windows 7 do not establish real BAR0 mapping, timing reads/writes, readback,
or restore behavior on a supported NVIDIA card. No hardware write IOCTL was
sent during this validation. Those hardware checks remain a separate step
on a compatible card and its Windows 7 NVIDIA driver.
